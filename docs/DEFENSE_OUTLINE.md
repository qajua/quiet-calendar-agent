## 高概率追问：建议回答要点

1. **“这算手机 Agent，还是电脑脚本？”** 任务由手机通知触发，日历变化发生在同一台手机；电脑负责规划、审批和传输。当前是“云端大脑＋手机执行器”架构的本地原型，不宣称通用手机自动化。
2. **“为什么不用无障碍点击？”** 无障碍点击会使用同一个前台、焦点和键盘，与题目的同时使用条件直接冲突；Calendar Provider 在后台写数据，不需要占屏。
3. **“怎么证明没有打扰？”** 连续录像呈现使用者输入；执行日志采样前台 App/键盘状态，并记录手机端独立回读。采样有间隔，不能单独证明绝对零闪动。
4. **“模型理解错了怎么办？”** 输出受 JSON Schema 约束，遇到歧义会停下提问；执行器再做事件唯一匹配、时间与冲突校验、写前状态比对。当前控制台是批准通知原文，尚未实现批准具体计划，因此这也是下一步改进点。
5. **“误改用户日历怎么办？”** 当前改期目标必须带 Agent 创建的任务标记；字段变化则拒绝修改/撤销。演示不处理任意外部创建事件。
6. **“失败一半会怎样？”** 每个子任务留日志；已完成步骤反向补偿。若断电或回滚再次失败，日志保留 `rollback_failed`，需要人工核对；目前没有生产级持久恢复队列。
7. **“能在 iPhone 或所有安卓上跑吗？”** 不能。当前只验证 Android 模拟器和华为 Mate 40 Pro；iOS 没有对应部署，其他品牌需要真实兼容性测试。
8. **“通知里的文字可靠吗？”** 不可靠。只允许明确配置的来源 App；来源包名不代表发送者可信，所以不会让通知自动修改日历，高风险词直接阻断，中风险要求电脑确认。生产环境还需要更细的身份核验与授权。

## 自己先复盘的两个薄弱点

- 控制台现阶段把“创建日程”识别成中风险，但对应的通知执行器尚未实现自然语言创建；演示应使用已经验证的改期复合任务，不把未支持路径说成完成。
- 模型 API Key 只在用户自己的终端中提供；最终通知→确认→执行的实机录像完成前，不要声称这一整段已验证。
- 时间解析烟测：以 `2026-09-21T10:00:00+10:00` 为参考，“本周三下午三点”应得到 `2026-09-23T15:00:00+10:00`，省略“本周”时应要求澄清；事件是否唯一由执行器检查。
